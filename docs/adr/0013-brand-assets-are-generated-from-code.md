# Brand assets are generated from code, and each route's Open Graph card is drawn on request

The Ritools brand assets are built by scripts, not drawn and not generated by a model. `apps/web/scripts/generate-brand-assets.ts` writes the PWA icon set and the glyph atlas; `apps/web/scripts/capture-pwa-screenshots.ts` writes the manifest screenshots from the running app. The letters are outlines taken from the self-hosted WOFF2 files under `apps/web/public/fonts`, and the cut of the wordmark is the cut of the `Ransom` component, read from the same module the component uses (`apps/web/src/core/libs/ransom-cut.ts`). The script fails when the stylesheet and that module disagree, so the wordmark the navbar draws and the wordmark the card draws cannot drift apart.

The wordmark is not a shipped file: the navbar and the card draw it from code, and nothing named `wordmark` lives under `public/`. The compact mark is gone, and the logo is a supplied raster ([ADR-0014](./0014-the-logo-is-a-supplied-file.md)): `generate-brand-assets.ts` reads `public/logo.png` and cuts the icon set from it, and it never writes the logo.

The Open Graph card is an endpoint, `GET /api/og`, not a file the build writes. `apps/web/src/routes/api/og.ts` answers with the card of the site, or of one Tool from the Tool Catalog, and the composer in `apps/web/src/features/og` draws it on request. Each route keeps its own card and names it with `ogImagePath`; only the delivery changed, from a committed artifact to a drawn response.

The earlier record rejected on-request rendering because it "puts an SVG rasterizer inside the Nitro runtime on a host that is not fixed". Both halves of that sentence are now decided otherwise. The app is aimed at Cloudflare (`apps/web/README.md`), and the card must run on a Worker as well as on Node, so the renderer is `@resvg/resvg-wasm`, a WebAssembly module fetched from `public/resvg.wasm` once per process — not a native module, and not inlined into the server bundle. The host is fixed enough to accept a Wasm rasterizer, and the card is the only thing that needed one.

The letterforms come from a glyph atlas: `bun brand:gen` measures every character of the print charset in every brand face, in em, and writes `apps/web/src/features/og/glyph-atlas.generated.ts`. The card cannot read a WOFF2 file or hold a font parser, so it scales outlines it already has. The atlas is a committed artifact and a unit test fails when the font files and its recorded digests disagree.

Where the chips of the wordmark sit is **one** implementation, `apps/web/src/core/libs/brand/ransom-layout.ts`: the card reads it to place every chip and letter, and it takes the cut from `ransom-cut.ts`, which the `Ransom` component renders with. The card and the navbar therefore say the same name in the same cut.

## Considered Options

- Keep the cards as committed files, one per route — rejected; a new Tool then needs a build and a commit before its card exists, and every Tool shares the copy of the day the script ran.
- A single card for the whole site — rejected; every Tool would share one face.
- `satori` and a JSX card, the way a Next.js app writes `next/og` — rejected; `satori` has no path drawing, so the ransom wordmark would be rebuilt from divs and would stop matching the navbar. The reference was worth copying for its shape (a params module, one card function per kind, fonts read once), not for its renderer.
- `@resvg/resvg-js` or `sharp` — rejected; both are native modules and do not run on a Worker.
- Inline the Wasm with `?url&inline` — rejected; 2.4 MB of base64 in every server bundle, for a module that is fetched once per process.
- Read the fonts at request time with `fontkit` — rejected; a font parser and a WOFF2 decompressor in the server bundle, and per-cold-start parsing of files the atlas already measured.
- Draw the brand assets by hand, or generate them with a model — rejected; the wordmark must be the component's cut, and every raster the scripts write must carry the line that says where it came from.

## Consequences

A card changes when the catalog or the copy changes, with no build and no commit. The response carries `cache-control` and an `ETag` over the drawing itself, so a feed that holds a current card gets a `304` and the raster is never redrawn. The endpoint answers `500` with `no-store` when it cannot draw, so a broken card is never cached.

The card is a server-only module: the route imports `og.card.server.ts`, not the composer (`og.drawing.ts`), so the glyph atlas (about 290 kB) and the painter stay out of the browser bundle. `bun build:worker` and a CI step keep a Node-only import from landing in this path later.

Two things can now be stale in a way they could not before: the atlas against the font files (guarded by a test), and `public/resvg.wasm` against the installed `@resvg/resvg-wasm` (copied by `scripts/copy-resvg-wasm.ts` before `dev` and before `build`). A card that renders empty letters means the atlas is older than the fonts; a card that fails to load means the copy did not run.

The icon set and the manifest screenshots stay committed artifacts, and the build ships them as they are: `pwaAssets` is not set in `apps/web/vite.config.ts`, so the icons are not cut again at build time. A change to the logo is a run of `bun brand:gen`, not a dropped file into `public/`. Every shipped raster the scripts write carries its origin in a PNG `tEXt` chunk, so `impeccable embed-prompt --scan apps/web/public` reports nothing missing. No asset holds an embedded font, and no image comes from a model.

Adding a Tool needs no poster step: the card endpoint reads the Tool catalog, so a new Tool gets its card and its route names it. The card is in the first language the site ships, because the Locale is a cookie and not a path, and one URL has one image.
